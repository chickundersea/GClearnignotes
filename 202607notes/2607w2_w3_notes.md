### floor()取整數










目前產報表 script 會頻繁遇到 checksum error 導致報表產出中斷。
重新盤點 codebase 後找到根因，整理如下供評估：

1. 根因：帳單金額被重複計算（膨脹）
目前在撈帳務資料時 主資料查詢的 script 會用配對的方式（JOIN permi ），會拿 user 的權限設定去比對帳單。當一個 user 的權限有重疊時，同一筆帳單會被撈出多次。
舉例：     
    -  假設 user_XXX 的權限設定有兩筆：

        a.「可以看 payer-A 底下所有帳號」
        b.「可以看 payer-A 底下的 account_111 帳號」
        當系統去撈 account_111 帳號那筆 $100 的帳單時，a、b兩筆權限都配對成功 → 同一筆帳單被撈出來兩次 → 加總變成 $200。
        --> 但實際上應該是 $100，但報表算出來是 $200。
    - 現行的 checksum 機制 就是去檢查這個，會用另一種叫 「EXIST」的方式（不會重複的方式）再算一次總金額，然後比對兩邊是否一致。如果不一致就報錯，然後中斷後面的計算。
  
2. 建議修法：
   - 把 主資料查詢的 script 直接改為另一種叫 「EXIST」的方式（不會重複的方式）， 逐列檢查 permission，所以不管 user 的權限設定多重複，帳單都只會被算一次，能夠根本消除膨脹問題（上述的重複計算）。
   - 改完之後因為已經沒有膨脹問題，checksum 機制就沒有存在檢查的必要性，因為用同樣的方法對同樣的資料算兩次一樣的東西，永遠會相等，沒有保護效果。且這邊的檢查本來就對後續的折扣計算、手動調整、匯率轉換等都沒有驗證能力。
   - 拿掉 checksum 可以省掉每次 Athena query 這段的時間與費用。

3. 影響範圍與風險: 
   - 修改範圍：僅帳單撈取的權限篩選邏輯，不影響後續折扣計算、匯率轉換、Excel 格式產出。
   - 風險：低。新寫法就是 checksum 已經在用的邏輯，等於把「驗證端」已驗證正確的做法套用到「主查詢端」。
